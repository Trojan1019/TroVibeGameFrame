# AgentDoc

本目录是这个项目的执行约束和设计事实来源。后续 AI 代理进入项目时，应先读这里，再开始分析或改代码。

## 项目定位

这是一个“游戏流程壳优先”的 AI 生成游戏项目，不再把当前样例直接当成最终成品。

当前仓库里保留的数字合成玩法，只是一个过渡期 sample module，用来承载：

- 登录和大厅壳层
- 对局进入和退出
- 结算页
- 任务、邮件、商店、背包、排行等外围系统
- SDK 接入和本地状态流转

## 当前开发思路

1. 先把“流程框架”抽出来，再替换玩法，不反过来做。  
   目标是先稳定大厅 -> 对局 -> 结算 -> 回流这一套流程，再逐步接新玩法模块。

2. 允许旧 gameplay 暂时存在，但它不应该再决定项目方向。  
   旧的 2048-like 对局可以保留，作为占位、回归验证和数据流测试模块。

3. 对局页优先支持“快速完成流程”。  
   右上角应保留正式的“关卡胜利 / 关卡失败”快速完成按钮组，用来跳过实际游玩，直接验证流程、结算、奖励和外围系统。

   这类流程控制 UI 应尽量做成共享组件，而不是写死在某一个玩法实现里。

4. 新玩法接入时，优先替换模块，不优先重写整页。  
   现阶段更倾向于：
   - 保留 `gameFlow`
   - 通过 `games/registry` 选择当前激活玩法
   - 通过 active game adapter 提供 snapshot、任务事件、胜负判断等玩法元信息
   - 保留共享壳层
   - 让 `playing` 页维持“共享容器 + 模块视图”的结构
   - 把具体玩法从 sample module 逐步替换为新的 module

5. 壳层 UI 的视觉迁移，优先通过本地 wrapper 层完成。  
   现阶段不要把外部风格库直接散落到业务页面里，更倾向于：
   - 在共享层维护 `shell` primitives
   - 业务页只依赖按钮、面板、标题、钱包、弹窗等 wrapper
   - 先替换 Lobby / Settlement / 共享弹窗 / 状态面板
   - 后续如果切换另一套美术风格，优先替换 wrapper，不直接改业务状态流

6. 用户可见层先去 2048 成品化，再处理内部命名。  
   只要用户看见的页面还像“2048 成品”，就优先处理可见文案、入口和交互。内部 `game2048`、`missions2048`、旧 localStorage key 可以后续再迁移。

## 具体落地原则

- 小步修改，优先局部补丁。
- 优先复用现有组件和状态流，不大改结构。
- 共享壳层的改动优先级高于样例玩法细节。
- 分数展示、快速完成、结算入口等流程控制 UI，优先抽成共享组件。
- 任何新玩法尝试，都尽量接在现有流程框架上验证。
- 未经明确要求，不做大规模重命名、重构或清理。

## 当前阶段目标

### Phase 1

抽出流程骨架：

- `lobby`
- `playing`
- `settlement`

### Phase 2

弱化 sample gameplay 对流程验证的绑定：

- 在对局页提供正式的快速完成按钮组
- 可以不实际游玩，直接走胜利 / 失败结算

### Phase 3

把 `playing` 视为“可插拔模块容器”：

- 旧 sample module 保留
- 新玩法模块逐步接入
- 在切换期允许多个玩法并存

### Phase 4

当新玩法稳定后，再处理：

- 内部命名迁移
- localStorage key 迁移
- sample module 的降级或移除

## 对后续 Agent 的要求

- 先读 `AgentDoc/README.md`
- 优先服务“流程先行、玩法渐进替换”这个方向
- 如果用户要做新玩法，先考虑如何挂到现有流程壳上
- 每次改动后至少验证 `npm run lint` 和 `npm run build`
- 每次改动结束后，检查 `npm run dev` 是否仍在运行；如果 `localhost:3005` 没有监听，就重新启动项目。
- 如果用户当前就在 in-app browser 看 `http://localhost:3005/`，改动后默认帮用户把项目重新打开到可访问状态；若浏览器策略阻止自动重载，至少确保本地 dev server 已恢复，并明确提示用户刷新当前页。
