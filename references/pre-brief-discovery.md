# Pre-Brief Discovery

Use this before writing the full Game Design Brief when the user gives a partial game idea.

Partial ideas include:

- A genre only
- A reference game only
- A mix of references, such as "Spider Solitaire + Balatro-like"
- A theme with no core loop
- A mechanic with no target device
- A request that lacks style, layout, feedback, or delivery level

## Required Output

Output these sections and then stop:

### Known Direction

Summarize what is already clear from the user request.

### Missing Decisions

List the decisions that block a solid Game Design Brief.

Use this checklist:

- Target device and viewport
- 2D/3D and rendering approach
- Core mechanic and player verb
- How reference games are fused
- Session length
- Delivery level
- Phase flow
- Win/completion condition
- Lose/failure/pressure condition
- Positive feedback
- Negative feedback
- Visual style
- Layout intent and layout archetype
- Performance/browser interaction constraints

### Recommended Defaults

Offer concrete defaults that Codex can use if the user wants to move quickly.

Defaults should be specific enough to become a Game Design Brief.

### Questions

Ask 3-6 questions. Prefer questions that change the game design materially.

Good questions:

- Which device and viewport should be primary?
- Which reference contributes the base rule system, and which contributes meta-combo/reward?
- Should the session feel relaxing, strategic, risky, or explosive?
- What should cause failure or pressure?
- What layout should dominate the game screen?
- Should Codex choose the visual style and defaults?

Do not ask more than 8 questions at once.

## Continue Rule

After Pre-Brief Discovery, wait.

Continue to Game Design Brief only when the user:

- Answers the questions
- Says Codex can decide
- Says to use the recommended defaults

Do not write implementation code during this phase.
