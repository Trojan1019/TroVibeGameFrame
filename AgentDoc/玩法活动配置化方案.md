# 玩法活动配置化方案

这份文档定义“玩法模块”和“外围活动”之间的解耦方式，目标是：

- 更换玩法时，不重写 Lobby / 活动入口 / 邮件 / 任务 / 商店结构
- 不依赖 AI 每次手工改按钮、文案、入口顺序
- 允许通过配置切换不同玩法模式、赛季包、活动包

---

## 1. 核心原则

配置化的边界不是“所有东西都不用代码改”，而是：

1. 玩法只负责产出标准事件
2. 外围活动只消费标准事件和配置
3. 壳层页面只负责按配置渲染入口和模块

不要让外围系统直接理解玩法内部规则。

例如：

- 弹球玩法知道什么叫“连击”
- 2048 玩法知道什么叫“最大 tile”
- 外围任务系统不直接懂这些玩法细节，只接收统一事件

---

## 2. 四层结构

### 2.1 Game Adapter

每个玩法模块负责：

- 暴露玩法状态
- 暴露胜负和结算信息
- 把玩法内部行为转换成标准事件

例如：

- `round_started`
- `round_finished`
- `score_reached`
- `combo_reached`
- `item_used`
- `currency_spent`
- `rank_submitted`

### 2.2 Activity Pack

活动包只定义：

- 要开哪些外围活动
- 任务模板
- 邮件模板
- 签到奖励
- 商店包
- 排行榜文案
- 活动入口排序和显隐

### 2.3 Shell Layout

壳层只定义：

- Lobby 显示哪些入口
- 哪些入口在主导航
- 哪些入口在浮层按钮
- 哪些入口隐藏

### 2.4 Runtime Manifest

运行时清单只负责把当前模式拼起来：

- 当前玩法模式
- 当前活动包
- 当前壳层布局

---

## 3. 推荐目录

统一使用：

```text
Game/public/config/
  current-mode.json
  modes/
    pinball-pet.json
  activity-packs/
    pinball-season-s1.json
  shell-layouts/
    pinball-lobby-v1.json
```

说明：

- `current-mode.json`
  运行时入口，只决定当前加载哪几份配置

- `modes/*.json`
  面向玩法模式的配置，决定 mission group、默认玩法文案、事件映射语义、默认外部包

- `activity-packs/*.json`
  面向外围系统的配置，决定签到、任务、邮件、商店、排行榜等

- `shell-layouts/*.json`
  面向界面骨架的配置，决定 Lobby 入口和页面模块显隐顺序

---

## 4. 推荐运行时模型

### 4.1 当前模式清单

```json
{
  "modeId": "pinball-pet",
  "activityPackId": "pinball-season-s1",
  "shellLayoutId": "pinball-lobby-v1"
}
```

### 4.2 Mode Config

模式配置只描述玩法语义，不承载完整活动内容。

例如：

- 玩法显示名
- missionGroupCode
- 默认分数语义
- 可上报的标准事件种类
- 对局页按钮文案

### 4.3 Activity Pack Config

活动包配置承载：

- 签到奖励
- fallbackDaily
- fallback mail
- 商店商品
- 排行榜页文案
- 活动入口 badge 规则

### 4.4 Shell Layout Config

壳层布局配置承载：

- 主入口列表
- 浮动入口列表
- 默认隐藏入口
- 入口顺序
- 是否启用某些外围模块

---

## 5. 哪些适合配置化

适合纯配置化：

- 签到奖励
- 邮件 seed
- 商店商品
- 任务模板
- 活动入口排序和显隐
- Spine 立绘引用
- 活动标题、副标题、提示文案
- 排行榜页文案和入口开关

不适合硬做成万能配置：

- 玩法内部规则
- 复杂结算逻辑
- 强玩法耦合的数值判定
- 复杂任务条件计算

这类应由玩法 adapter 先转成标准事件，再交给外围配置消费。

---

## 6. 推荐迁移顺序

第一步：

- 先保留现有 `GameConfig`
- 只新增 `mode manifest / activity pack / shell layout` 协议和样例文件

第二步：

- 让 `runtimeConfig` 支持读取 `current-mode.json`
- 读取对应的 mode / activity / shell 三份配置
- 组合成一个运行时配置对象

第三步：

- 优先把 `LobbyScreen` 的入口渲染从写死改成读 shell layout

第四步：

- 把 `App.tsx` 里的签到 / 邮件 / fallback 任务来源改成 activity pack

第五步：

- 把任务系统从“按 2048 类别词汇驱动”逐步迁到“统一标准事件驱动”

---

## 7. 当前仓库建议

当前项目最适合先做：

1. 增加配置协议文件
2. 增加样例 JSON
3. 增加组合加载器
4. 不立刻重写主页面逻辑

这样能先把结构固定住，再逐步把实际 UI 和外围逻辑迁过去。

这是本次推荐的实施顺序。
