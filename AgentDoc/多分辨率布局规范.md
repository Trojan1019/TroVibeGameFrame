# 多分辨率布局规范

这份文档用于约束当前项目在固定逻辑画布下的布局适配方式。

目标不是让所有分辨率长得一模一样，而是让它们都遵守同一套布局纪律：

- 结构不漂
- 主动作不丢
- 关键 HUD 不遮挡
- 高度差异只影响留白和密度，不改变交互逻辑

---

## 1. 先定义：当前项目不是普通响应式网页

当前项目已经进入“固定开发基线 + 固定显示基线 + 测试机型预览”的模式。

因此适配原则不是：

- 根据浏览器窗口宽高直接做网页自适应

而是：

- 先确定开发基线尺寸
- 再确定显示安全框基线
- 最后用不同测试机型去验证缩放结果

禁止直接使用：

- `window.innerWidth`
- `window.innerHeight`
- 依赖真实浏览器外层尺寸的页面布局判断

页面应只依赖逻辑画布尺寸。

---

## 1.1 当前项目基线

当前固定基线如下：

- 开发基线：`750 × 1624`
- 显示安全框基线：`390 × 844`

解释：

- `750 × 1624` 用来定义当前项目的开发预览默认尺寸和资源输出参照
- `390 × 844` 用来定义当前 UI 的观感基准，也就是“当前看起来最对”的手机显示比例
- 不同测试机型不再直接改 UI 组件尺寸，只负责验证这套安全框在不同屏幕下如何缩放、留白、居中和承载

这套策略更接近 Unity `Canvas Scaler / Scale With Screen Size` 的思路：

- 先有一套参考分辨率
- 再有一套内容安全框
- 额外空间优先给背景和节奏，不优先拉伸控件本体

---

## 2. 布局模式

当前项目统一按 5 种布局模式处理：

### 2.1 `compact`

适用：

- 小屏竖版
- 典型如 `375×667`

特点：

- 垂直空间紧
- 标题与外围入口容易互相挤压
- 主内容区必须压缩密度

要求：

- Header 压缩
- 标题单独占区
- 双侧工具位缩小
- CTA 区高度缩小但仍固定在底部

### 2.2 `standard`

适用：

- 常规手机竖版
- 典型如 `390×844`、`412×915`

特点：

- 作为默认参考布局
- 不需要强压缩，也不需要特意拉伸

要求：

- 使用标准字号、间距、按钮尺寸
- 主玩法区与底部 CTA 区按默认节奏分布

### 2.3 `tall`

适用：

- 超高屏
- 典型如 `900×2000`、`1080×1920`

特点：

- 可用高度很大
- 如果直接等比拉伸，页面会显得“空”

要求：

- 不拉伸按钮和 HUD
- 额外高度优先给留白和节奏
- 让 CTA 始终稳定在底部
- 中心内容区可以适度放大，但不失控

### 2.4 `landscape`

适用：

- 宽屏横版
- 典型如 `1624×750`

特点：

- 宽度富余，高度紧张
- 最容易出现内容挤压和上下区争抢

要求：

- 核心内容区使用“contain”思路，不强行铺满
- 顶部功能区压缩
- 重点保护主要玩法区和 CTA 层级
- 允许出现两侧留白，但不允许主交互失位

### 2.5 `tablet`

适用：

- 平板或接近平板比例

特点：

- 既有高度也有宽度
- 最容易出现“全部元素显得过小”

要求：

- 提升主视觉尺寸
- 放大标题、英雄元素和统计卡
- 保持主 CTA 权重不下降

## 3. 页面结构规范

### 3.1 Lobby

Lobby 必须拆成四个区：

1. `header zone`
   头像、钱包、邮件
2. `title zone`
   title chip、主标题、说明文案
3. `hero zone`
   中心形象 + 双侧外围入口
4. `cta zone`
   开始示例 / 继续进度

禁止：

- 用固定 `top` 值把双侧入口钉在页面上
- 让标题和双侧入口处于同一绝对定位层互相压
- 让 CTA 通过自然文流飘在页面中部

Lobby 的适配规则：

- `compact`：标题区独立，双侧工具区缩小，CTA 区减高
- `standard`：维持标准布局
- `tall`：额外高度给 hero zone 与上下节奏，不放大 CTA
- `landscape`：允许中心内容变窄，但 CTA 仍固定在底部

### 3.2 Playing

Playing 必须拆成：

1. `top action zone`
   返回、重开、状态面板
2. `wallet zone`
   金币与宝石
3. `playfield zone`
   玩法主操作区
4. `status / guidance zone`
   反馈条、引导条
5. `tool zone`
   方向操作、道具操作

规则：

- 棋盘尺寸必须基于逻辑画布计算
- 不能继续按真实浏览器宽度算
- 棋盘优先满足“看得清”和“保留工具区”
- `landscape` 下优先保护棋盘，不强迫其铺满宽度

### 3.3 Settlement

Settlement 必须拆成：

1. `nav zone`
2. `result hero zone`
3. `stats zone`
4. `return action zone`

规则：

- 结果图标、标题、统计、回流按钮层级固定
- 高度不足时先压缩装饰，不压缩回流动作

## 4. 尺寸调节原则

### 4.1 哪些东西可以变

允许变化：

- 字号档位
- 留白
- 组件间距
- 英雄插画尺寸
- 工具位尺寸
- 棋盘尺寸

### 4.2 哪些东西不应随便变

不应随便变化：

- 页面区块顺序
- 主 CTA 的相对权重
- HUD 的语义位置
- 奖励层与反馈层的逻辑关系
- modal 的交互方式

---

## 5. 留白规范

高屏和宽屏出现空白，不等于适配失败。

当前项目允许的空白：

- 用于呼吸感
- 用于主题背景层
- 用于把主操作区和 CTA 区分开

不允许的空白：

- 让主区块看起来散掉
- 让用户误以为中间缺内容
- 让 CTA 与主内容断开到像两个页面

规则：

- 额外空间优先加给“区块之间”
- 不优先加给“单个按钮内部”
- 不优先加给“单个面板高度”

---

## 6. 绝对定位规范

允许绝对定位的内容：

- 装饰漂浮物
- 徽章
- 红点
- 奖励飞行层
- 教程焦点层

不建议绝对定位的内容：

- 主要导航
- 双侧工具栏主位置
- CTA 主按钮区
- 会随分辨率漂移的正文结构

结论：

- 绝对定位只用于“装饰层”和“临时层”
- 结构层优先用 grid / flex 分区

---

## 7. 当前项目适配总结

本轮适配收敛出的结论是：

1. 适配不能再按页面临时修值
2. 必须先归类逻辑画布模式
3. 结构层不能继续依赖固定像素 `top`
4. 棋盘和主视觉尺寸必须从逻辑画布推导
5. 高屏处理重点不是“拉满”，而是“稳住节奏”
6. 横屏处理重点不是“铺满”，而是“保护核心区”

---

## 8. 后续新增页面的要求

以后新增页面或新玩法模块时，至少先回答这几个问题：

1. 这个页面属于哪一类结构：
   - `header + hero + cta`
   - `hud + playfield + tools`
   - `result + stats + return`
2. 在 `compact / tall / landscape` 下，它的主区块顺序是否不变
3. 是否有结构层误用绝对定位
4. 是否直接读取真实浏览器窗口尺寸
5. 额外空间是被当成“节奏留白”，还是被错误地拉长了组件
