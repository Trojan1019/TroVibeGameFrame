# 框架交互规范

这份文档不是某个单一玩法的设计稿说明，而是当前项目后续做玩法替换、壳层升级、UI 迁移时都应遵守的交互框架规范。

它的目标是把 [`交互迁移经验文档.md`](/Users/Trojan/VibeCodingGame/Project_2/交互迁移经验文档.md) 里可迁移的经验，整理成项目级、框架级、可执行的交互约束。

适用范围：

- 大厅、对局、结算三段式流程
- 共享 HUD、共享弹窗、共享奖励层、共享教程层
- 未来替换 2048、三消、合成、轻解谜等具体玩法模块

不直接负责的内容：

- 具体玩法规则设计
- 具体美术风格包的完整 token 定义
- 某一个页面的像素级排版细节

---

## 1. 总目标

这个项目的交互目标不是“动画多”，而是让用户在最短时间内形成下面 4 个感知：

1. 我现在在哪个流程阶段
2. 我现在能做什么主动作
3. 我刚才的操作是否成功
4. 奖励、进度、结算为什么发生

如果一个页面视觉上更好看了，但这 4 件事没有更清楚，就不算交互升级。

---

## 2. 总原则

### 2.1 主动作单一

任意时刻只能有一个最显眼的主动作。

要求：

- 首屏只允许一个进入动作
- 对局中只允许一个核心操作路径最突出
- 弹窗中只允许一个主 CTA 最强
- 结算页只允许一个回流动作最强

禁止：

- 同层级放多个高权重按钮
- 既要用户操作棋盘，又同时让他关注多个弹窗入口
- 所有按钮都做成高饱和主按钮

### 2.2 反馈必须分层

不要把“预判、提交、结果、奖励”做成一个混合动画。

必须拆成四层：

1. `preview`
   用来告诉用户“如果现在提交，会发生什么”
2. `commit`
   用来告诉用户“动作已经被接受”
3. `result`
   用来告诉用户“状态已经改变”
4. `reward`
   用来告诉用户“收益去了哪里”

### 2.3 高频反馈克制

高频发生的动作只允许改 1 到 2 个维度。

建议：

- 候选态主要改透明度、描边、轻微 glow
- 成功态主要改脉冲、短时 scale
- 失败态主要改底色、轻微抖动、提示文案

禁止：

- 高频状态同时旋转、缩放、闪白、爆粒子
- 所有状态都长时间发光
- 所有点击都做重动画

### 2.4 教程只教当前动作

教程层不负责解释系统全貌，只负责把“当前必须学会的一步”讲清楚。

要求：

- 一次只教一个动作
- 用真实焦点区和手势引导，不用长段说明文
- 可交互区域必须真实可点
- 教程层必须跟随目标位置，不允许写死坐标

### 2.5 奖励要可追踪

奖励不能只表现为数字变化，必须尽量形成来源到目标的因果链。

优先级：

1. 有真实来源
2. 有真实目标
3. 有飞行或迁移动画
4. 到达目标后再更新目标状态

## 3. 框架层级

整个项目的交互层建议固定分成下面 6 层：

### 3.1 流程层

负责：

- `lobby`
- `playing`
- `settlement`
- 流程切换
- 回流关系

不负责：

- 单一玩法的具体输入细节

### 3.2 模块交互层

负责：

- 具体玩法的核心输入
- 手势、点击、拖拽、键盘等主操作
- 玩法内部预判和提交

要求：

- 只处理玩法相关输入
- 不直接管理全局壳层视觉风格
- 不把奖励飞行、全局教程、流程按钮写死到玩法规则模块里

### 3.3 壳层 HUD

负责：

- 顶部数值
- 快速完成
- 共享工具位
- 共享状态提示

要求：

- 作为流程容器的稳定锚点
- 不随具体玩法大幅重排
- 奖励层要以 HUD 为落点，而不是以玩法模块内部节点为落点

### 3.4 反馈层

负责：

- 无效反馈
- 成功反馈
- 预判反馈
- 状态 Banner

要求：

- 优先短时、轻量、可撤销
- 不遮挡主操作区域

### 3.5 奖励层

负责：

- 分数增长反馈
- 奖励飞行
- 里程碑庆祝
- 结算前后的资源转移感

要求：

- 使用独立浮层
- 基于来源和目标的真实坐标
- 动画结束后销毁临时节点

### 3.6 教程层

负责：

- 焦点挖空
- 手势演示
- 当前动作限制

要求：

- 只在首次学习或关键切换点出现
- 只放行当前应操作区域
- 教程逻辑与页面布局解耦

## 4. 页面级交互规范

### 4.1 Lobby

职责：

- 建立题材气质
- 提供唯一主入口
- 提供次级外围系统入口

要求：

- 主 CTA 必须最显眼
- 外围系统入口必须明显低于主 CTA
- 用户第一次看到 Lobby 时，应该先知道“怎么开始”，再知道“还有什么”

### 4.2 Playing

职责：

- 承载单一核心玩法
- 给出即时反馈
- 挂接奖励层与教程层

要求：

- 中心视觉始终留给主玩法区域
- HUD 不应覆盖主要操作核心区
- 对局内流程控制按钮必须稳定存在
- 快速完成是流程验证组件，不应被藏进深层菜单

### 4.3 Settlement

职责：

- 明确胜负结果
- 总结本局关键指标
- 引导用户回流

要求：

- 结果、奖励、下一步动作三者层级清楚
- “再来一局”和“回大厅”必须有明确主次
- 庆祝动画可以存在，但不能抢掉回流动作

## 5. 状态分层规范

禁止把所有 UI 状态混成一个大对象而不分边界。

至少应分成下面四组：

### 5.1 页面状态

```ts
type Screen = "lobby" | "playing" | "settlement";
```

### 5.2 交互状态

```ts
type InteractionState = {
  activeTool: string | null;
  drag: object | null;
  selectedTargetId: string | null;
  preview: object | null;
  feedbackTone: "idle" | "success" | "invalid";
};
```

### 5.3 教程状态

```ts
type TutorialState = {
  step: string | null;
  completed: boolean;
  target: object | null;
};
```

### 5.4 奖励状态

```ts
type RewardUiState = {
  flights: object[];
  milestone: object | null;
  burstNonce: number;
};
```

原则：

- 页面状态决定“在哪一屏”
- 交互状态决定“手现在在做什么”
- 教程状态决定“现在允许学什么”
- 奖励状态决定“哪些反馈要发射”

## 6. 反馈规范

### 6.1 响应时限

主操作反馈必须在 `150ms - 800ms` 内可见。

建议：

- 预判反馈：即时
- 成功提交：`180ms - 420ms`
- 明显结果反馈：`240ms - 560ms`
- 奖励飞行：`520ms - 760ms`

### 6.2 无效反馈

无效反馈必须温和但明确。

允许：

- 轻微 shake
- 短时变色
- 简短状态文案

不建议：

- 大幅位移
- 高频重复抖动
- 整屏强闪

### 6.3 成功反馈

成功反馈必须比无效反馈更稳定、更短促、更有“落地感”。

建议：

- 短脉冲
- 轻微放大再回落
- 局部高亮

---

## 7. 奖励层规范

### 7.1 独立浮层

奖励飞行必须放在独立的 flight layer 中。

推荐流程：

1. 读取来源 rect
2. 读取目标 rect
3. 转成同一坐标系
4. 创建 flying node
5. 运行动画
6. 落点更新
7. 销毁临时节点

### 7.2 动画轨迹

奖励飞行不应是简单匀速直线。

推荐轨迹：

- 起点出现
- 中段放大
- 临近目标时过冲
- 回落并贴合目标

### 7.3 更新顺序

推荐顺序：

1. 来源先变化
2. 奖励起飞
3. 目标响应
4. 数值更新完成

禁止：

- 奖励还没飞到，目标先全部更新完
- 没有来源物就凭空弹奖励

---

## 8. 教程层规范

### 8.1 焦点策略

教程应使用“计算矩形 + 镂空遮罩”。

要求：

- 焦点框略大于真实点击区
- 按钮类目标建议 padding `10px` 左右
- 路径类目标建议 padding `24px - 26px`
- 点击焦点最小可视尺寸不低于 `88px`

### 8.2 手势策略

要求：

- 拖拽手势循环约 `1.8s`
- 点击手势循环约 `1.45s`
- 节奏偏慢，避免催促感

### 8.3 放行策略

只有当前应操作区域可以穿透。

禁止：

- 视觉高亮放行，但事件实际被罩层挡住
- 一次放开多个区域让用户猜

## 9. 视觉与组件落地规范

这部分不是完整美术规范，只定义框架交互必须满足的视觉纪律。

### 9.1 颜色分工

- 背景比可交互对象更淡
- 高饱和色只给结果、目标、奖励、主 CTA
- 错误色和成功色都尽量避免后台系统风

### 9.2 组件体积感

共享壳层组件应优先具备：

- 大圆角
- 厚描边
- 短阴影
- 内高光
- 柔和渐变

### 9.3 共享封装优先

视觉迁移优先落在共享 wrapper 层，而不是散落到业务页。

优先维护：

- `shell primitives`
- 共享 icon 映射层
- 共享奖励层
- 共享教程层

禁止：

- 业务页面各自复制一套按钮样式
- 不同 modal 各写一套图标语言

---

## 10. 工程边界规范

### 10.1 逻辑模块保持纯净

具体玩法规则模块尽量保持纯逻辑。

不要把下面内容塞进规则模块：

- 动画 nonce
- DOMRect
- 浮层节点
- 教程遮罩状态
- 壳层视觉样式

### 10.2 共享容器优先

未来新增玩法时，优先替换模块视图，不优先重写整页。

保持：

- 流程层稳定
- HUD 锚点稳定
- modal 入口稳定
- 教程/奖励层可复用

### 10.3 文档化优先

凡是后续会重复使用的交互规则，应沉淀进 `AgentDoc`，而不是只停留在一次聊天里。

建议沉淀内容：

- 资产命名规范
- 交互分层规范
- HUD / modal 优先级规范
- 奖励层规范
- 新玩法接入规范

## 11. 验收清单

后续任何交互升级，都至少用下面清单自查：

### 11.1 流程清晰度

- 用户是否能快速理解当前在 Lobby / Playing / Settlement 的哪一段
- 页面上是否只有一个主动作最突出

### 11.2 操作反馈

- 核心操作是否在 `150ms - 800ms` 内有可见反馈
- 失败与成功是否能被明确区分
- 预判是否早于提交

### 11.3 奖励因果

- 奖励是否有来源
- 奖励是否有目标
- 奖励是否形成了可追踪的转移链

### 11.4 教程有效性

- 教程是否只教一个动作
- 教程焦点是否跟随真实目标
- 放行区是否真实可操作

### 11.5 工程边界

- 样式是否优先沉淀到共享层
- 玩法逻辑是否仍保持相对纯净
- 共享壳层是否没有被新玩法强耦合污染
